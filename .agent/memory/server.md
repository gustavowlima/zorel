  - Executor (flows.ts): `runFlow` walks from the last step row (the next after a done or skipped one; a `running` row reruns that node). There is one `routine_run_steps` row per node: previews are `redact`ed and ≤4000, and the whole output goes in <dataDir>/runs/<routine>/<run>/<step>.json. HANDLERS is a dictionary. An agent step sends `flow:<stepId>:<attempt>` and waits for `onFlowTurn` (fed from runtime.finished in RoutineScheduler). Outside = the run has a payload.
  - Writes: `mayHaveWritten` is set right before the call and cleared on the answer. `resumeFlow` at boot: a running row with it set → `uncertain` + needs; else rerun (an agent step keeps its attempt while its turn is still queued or running). `resolveStep` (routines.ts): again, skip or stop.
  - Retries (`mayRetry`/`neverRan`): a read retries on any failure. A write retries only when listing (connect) failed or the server answered ParseError, InvalidRequest, MethodNotFound or InvalidParams; an `isError` result means it ran. Use `Effect.tryPromise({ try, catch: (e) => e })` there: the plain form wraps the McpError and hides its code.

Approvals use `runtime.requestApproval({ runStepId, … })`: `approvals.turn_id` is nullable, with `run_step_id` and a CHECK that exactly one is set. Boot expiry still expires them all, and the step reruns and asks again.

- useful routines (spec 012, 2026-11-10): every run is a `routine_runs` row (trigger, state queued/running/done, outcome nothing/something/needs, summary, report ≤4000, triage tokens, cost, held, delivered/note, read). clientId is `routine:<runId>`.
  - The outcome is the agent's last line `Outcome: …` (`OUTCOME_RULE` in schedule.ts, `outcomeOf` in routine-runs.ts). The line is removed from the saved reply (`setMessageText`). No marker means "something"; a failed or stopped turn means "needs".
  - A routine chat going `waiting` (approval, question) marks the run "needs" and delivers it at once, without delivering it again at the end.
  - The next run's prompt holds the last report (`lastReport`) plus `DELTA_RULE`.
  - Outside runs (a payload: webhook or watch) are queued, at most 20 per routine; the 21st gets 429 (`RoutineQueueFull`) and a "refused" row. The dispatcher runs one at a time per routine, never for a disabled routine, and ignores a busy chat because the runtime queues the turn behind. Scheduled runs still skip when busy.
  - `lookFirst` (webhook or watch): `ask(cheapModel)` with `triageText`. `act:false` ends the run "nothing" with no turn. Anything else, a timeout (20 s) or an error starts the agent. Triage tokens count in `agentTokensSince`.
  - Delivery: `shouldTell` (a table) with `inQuiet`, then the CHANNELS dictionary (notify = the `notices` RPC stream; telegram = `sayToPaired`, falling back to notify with "telegram not paired"; page = `savePage` with a version). Routine chats no longer give the generic web "done/failed/waiting" notifications.
  - Time profile (time-profile.ts, preferences): `timeZone`, `quietHours`, `dayStart {set, learned≤14}`, `lastActivityDay`, `briefAt`. Activity comes from `POST /api/activity` (web focus, ≤ every 10 min), an RPC send and a Telegram message. Cron uses the profile's zone. `onDayStart` routines run once per local day at the first activity or start + 3 h, from the 30 s tick. The brief goes to Telegram when a routine delivers there.
  - Today = `todayOf` over runs since `briefAt.previous`. Week = runs plus `plannedRuns` (≤200). History pages by 50; retention is 90 days keeping the newest 50 per routine, pruned daily from the routines tick.
  - Boot recovery: a running run whose turn didn't finish becomes "needs" ("Stopped by a restart").
