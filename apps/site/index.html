How a request moves

Say you want v1 of a small app ready: an empty-array bug fixed, tests for it, and a README that matches the code. You write that once, in plain words. You don't pick who does what.

  1. You ask Zorel. One message, to the lead.
  2. Zorel hands it out. The fix to Coder, the tests to Tester, the README to Docsync, each briefed with the project and what the team learned before.
  3. They work in parallel, each on the CLI it runs best on, in your project folder, on your sign-ins.
  4. Anything risky waits for you. Commands, deletes, pushes and payments stop at Zorel until you say yes.
  5. It lands, and stays undoable. The turn's diff sits under the reply, one click from undone, and what you taught the team is kept for the next chat.

What the team keeps between chats

A chat ends; the team doesn't start over. These stay with it, on your machine.

Any harness
Claude Code, Codex and OpenCode in the same chat, each on your own sign-in. When one hits its limit, the next in the fallback list picks up.
Memory and skills
Project notes, decisions and skills. A skill loads only when a message needs it.
Connectors
GitHub, Notion, Linear and others, signed in once. Writing anywhere asks you first.
The project, beside the chat
Files, Git, terminals, and a browser the agents drive, in one side panel.
Undo for every turn
A snapshot of the folder before and after each turn, whichever harness did the work.
